## Overview

FormatKit handles the tedious part of a clean Windows reinstall. Before formatting, a read-only checklist shows what would be lost. Afterwards, it detects the hardware and rebuilds the machine from a profile: a small JSON file that says what to set up. The documentation, in Portuguese and English, is on the [project site](https://jpst-dev.github.io/formatkit/).

## Features

- **Drivers**: Windows Update, vendor tools (Dell, HP, Lenovo), GPU driver, a report of devices missing drivers and a network driver backup for offline use.
- **Windows cleanup**: removes preinstalled apps and applies privacy, AI, interface and performance tweaks at three cumulative levels, with per-item undo.
- **Diagnosis**: `cleanup check` finds tweaks already applied on the PC that break or weaken Windows and shows the fix.
- **Programs**: installs from a catalog, from winget ids, from a `winget export` file of the old PC or from direct installers with a mandatory hash check.
- **Development environment**: WSL with a distro and user, Git, an SSH key and ssh-agent, dotfiles, zsh and Oh My Zsh, Oh My Posh and a Dev Drive with package caches.
- **Preparation checklist**: answers "is it safe to format?" by listing what to save first.
- **Graphical interface**: checklist, profile runs with per-step progress, hardware, diagnosis and catalogs.
- Text in Portuguese and English, following the Windows display language.

## Technical decisions

- **System access behind interfaces**: registry, files, processes, services and console go through `SystemAccess` interfaces. Steps never call Windows directly, so all the logic is tested with fakes: more than 1,700 unit tests, run in CI on every push.
- **One engine for the CLI and the UI**: composition lives in a shared project, and the WPF window uses the same engine as the terminal. The window runs unelevated and hands work that needs administrator rights to a separate process.
- **Reboot and resume**: a step can ask for a reboot; the run state is saved and a scheduled task picks up from the right point at the next logon. If the profile changes in between, the resume is refused.
- **Reversible, explained changes**: each cleanup item has a level and a description of what it breaks and what it gains, and every change goes into a journal that allows undoing it. Tweaks with no documented gain sit in the aggressive level, which requires an explicit confirmation in the profile.
- **Virtual machine testing**: the manual test script has 25 reproducible scenarios on a Hyper-V VM (network down, reboot and resume, cleanup and undo, development environment), driven by PowerShell scripts. Every problem found in the VM becomes a unit test.

## What I learned

- Designing code that changes the operating system so it can be tested without touching the system.
- Treating reboots as a normal part of the flow, with saved state and a safe resume.
- Separating an unprivileged interface from an elevated process, asking for permission only when needed.
